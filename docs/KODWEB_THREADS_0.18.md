# Обработчики HTTP и KS/DB в kodweb: проверка Thread ID

Проверен `kodweb.exe` 5.3.2.120 x86 на независимой копии полного комплекта. Исходный комплект не использовался для записи. Это исследование модели исполнения, а не новый замер скорости завершённых операций.

## Что подтверждено

В проверенных маршрутах **один и тот же рабочий поток обслуживает HTTP-соединение, выполняет KS/DB и остаётся занят при внешней конвертации**. Основание — совпадение Thread ID на одном TCP-соединении, рост CPU этого потока во время KS/DB и остановка роста CPU при заблокированном состоянии на стадии kdb/Excel. Это соответствует общему пулу обработчиков соединений и прикладных запросов, а не отдельному пулу KS, освобождающему HTTP-обработчик.

| Запрос | Thread ID в KeepAlive | Thread ID при Process | Дополнительная проверка |
|---|---:|---:|---|
| Предварительный обход DeleteObject | 7116 | 7116 | CPU потока вырос с 0,1094 до 122,4062 с за первые примерно 150 с наблюдения |
| Отчёт 1АС за 1 января 2025 года, StatOtchet221 | 5440 | 5440 | CPU рос при расчёте; на стадии kdb/Excel перестал расти, поток заблокирован |
| Однодневный реестр, convertToExcel | 7284 | 7284 | Тот же поток выполнял запрос на том же TCP-соединении |

ID относятся к одному запуску и не являются постоянными номерами исполнителей. Для удаления использован режим предварительного просмотра `fview=1`: проверялся обход связей, документы не удалялись. Поведение завершающей записи удаления этот опыт отдельно не проверяет.

## Ожидание конвертера

Примерно на 153,7-й секунде совместного наблюдения появился дочерний `kdb.exe` (PID 1620, родитель kodweb PID 14800), затем Excel PID 7276. Строка отчёта в status сохранила Thread ID 5440 и состояние Process. Между отметками 153,7 и 161,4 с его накопленное CPU оставалось 138,2031 с. Windows Wait Chain Traversal определял этот поток как blocked; полную цепочку до конкретного объекта ожидания WCT не раскрыл.

Excel создан в режиме `/automation -Embedding` через 0,11 с после kdb. Его открытый XLS совпал с выходным файлом в аргументах kdb. Совпадение времени запуска, файла и состояния потока связывает наблюдение с внешней конвертацией. Это не разрешённый стек конкретной функции ожидания и не доказательство того, что Excel выполняется внутри потока kodweb: Excel — отдельный процесс.

`/20a?convertToExcel` в этом комплекте — KS-режим генератора реестров. Имя маршрута не гарантирует запуск Excel: проверенный реестр формировался в HTML. Фактическое ожидание kdb/Excel проверялось отдельно на отчёте 1АС через `StatOtchet221`.

## Что добавляют настройки и справка

В `/admin?advanced` установлены максимум 40 потоков, резерв 20 потоков для соединений с локального адреса, Keep-Alive 10 с, предел памяти 3072 МБ и обновление хэша форм/поиска по времени каждые 600 с. Сжатие и DNS отключены. По описанию предел памяти допускает превышение на 20–30%.

В отдельной проверке status показывал 1 занятый / 39 свободных обработчиков. С двумя ожидающими KeepAlive-соединениями и запросом status — 3 / 37; после закрытия — снова 1 / 39. В Rust при тех же двух ожидающих соединениях и запросе status было 3 HTTP-соединения, 0 занятых KS/DB и 4 свободных исполнителя.

Резерв локальных соединений нельзя называть резервом интерфейса или считать доказанным делением 40 на 20+20: точное соотношение параметров и поведение при насыщении не проверялись. Наличие хэша форм/поиска не раскрывает устройство общего кэша индексов DB.

## Методика и границы вывода

Первый запрос на каждом сокете — status; затем, без переподключения и в пределах KeepAlive, отправлялся прикладной запрос. Отдельный наблюдатель сопоставлял порт соединения, Thread ID и URI в status с CPU системного потока. Использован сырой TCP-сокет с HTTP-парсером: автоматическое решение обычного HTTP-клиента закрыть соединение не должно подменить проверку нового запроса на старом сокете.

Проверка не доказывает устройство всех фоновых задач, FIFO-порядок очереди или отсутствие внутренних вспомогательных потоков. Она также не объясняет всю разницу скорости удаления: ранее измерены дополнительная работа, чтения и конкуренция за критические секции. Внутри каждого конвертера вызовы COM последовательны, но отдельные конвертеры могут работать одновременно.

После фиксации стадии конвертации эксперимент остановлен без ожидания готового отчёта. Это не успешный тест формирования XLS и не замер его полного времени.
