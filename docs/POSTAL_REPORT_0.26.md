# Почтовый отчёт — 0.26

## Почему страница оставалась пустой

`/20a?reportForPostServices` исполняет штатный KS из `spb.dbs`. Скрипт выводит заголовок, затем считает группы отправлений и печатает строки таблицы. kodweb передаёт этот HTML по ходу исполнения. Прежняя реализация Rust собирала весь текст в памяти и отправляла его только после завершения сценария.

В 0.26 готовый HTML передаётся во время расчёта. Отдельно ускорено повторное чтение строковых атрибутов в SQL. Состав запросов, строки отчёта и вычисление денежных сумм остаются штатными.

## Как передаётся результат

Расчёт `mode=1` выполняется в тяжёлой группе KS/DB. Исполнитель передаёт фрагменты через ограниченный канал в сетевую задачу Tokio. HTTP/1.1 использует `Transfer-Encoding: chunked`; HTTP/1.0 — ответ до закрытия соединения. Размер фрагмента не превышает 16 КиБ, канал хранит не более восьми событий. При заполнении канала медленным получателем выдающий поток приостанавливается.

Передача начинается с заголовка страницы. Следующие фрагменты отправляются на закрытии строки `</tr>`, при накоплении 16 КиБ либо при очередной записи после паузы не менее 100 мс. Новые фрагменты появляются, когда KS печатает результат; во время обработки запроса к базе вывода может не быть. `StartBuffMode` приостанавливает выдачу, `StopBuffMode` отправляет накопленный текст. Кодировка сохраняется Windows-1251.

Форма выбора периода остаётся обычным ответом. Потоковый режим включён для расчёта этого отчёта; остальные страницы и бинарные ответы работают как прежде. Проверка доступа выполняется до начала выдачи.

При отключении клиента расчёт отменяется. Если ошибка случилась после HTTP-заголовков, на странице появляется «Отчёт не завершён», а ответ обрывается без признака успешного окончания потока. Уже показанные строки не считаются полным отчётом. После успешного завершения постоянное HTTP-соединение можно использовать для следующего запроса.

## Где тратилось время расчёта

Сценарий отдельно запрашивает группы по массе и виду отправления. Для бандеролей два цикла проходят массы от 120 до 5000 г с шагом 20 г: всего 490 SQL-запросов, включая пустые группы. При включённом расчёте стоимости дополнительно читаются цены найденных писем. Строка появляется после завершения своей группы, поэтому интервалы между строками различаются.

На контрольном комплекте поле «Отправлено» индексировано, а строковое поле «Масса» — нет. После ограничения периода в `workbase/post.db4` оставалось 115 960 записей. Для каждой массы Rust снова разрешал их внутренние номера через MainKey, читал и полностью разбирал записи. Даже запрос по массе 3000 г с нулевым результатом занимал 1,71 с, из них 1,61 с — этот повторный просмотр. Только два цикла бандеролей могли повторно разобрать около 57 миллионов записей.

Теперь при первом таком запросе сохраняется колонка выбранного строкового атрибута: значения и соответствующие внутренние номера объектов. Следующий запрос с другой массой проверяет уже прочитанные значения. Используется тот же механизм сравнения SQL, включая регистр, «ё», маски, пустые строки и несколько значений одного поля. Порядок применения условий не меняется.

В отдельной проверке SQL построение колонки заняло 1,68 с. У 115 960 записей оказалось 93 различных значения массы; сохранённая колонка заняла около 598 КиБ по счётчику кэша. Следующий запрос, уже по массе 120 г, выполнился за 5,6 мс вместо прежних 1,71 с и вернул те же 38 объектов. Эта проверка изолирует ускорение отбора; чтение цен и формирование HTML в неё не входят.

Кэш общий для исполнителей KS/DB. Ключ содержит путь тома, поколение его изменений, область, атрибут и набор кандидатов. После проверки хеша сравнивается весь набор номеров: совпадения хеша или частичного списка недостаточно. Изменение и удаление объекта, а также восстановление журнала после сбоя меняют поколение. Незавершённое построение не публикуется; параллельные запросы не строят одну колонку одновременно.

В кэше сохраняется до 16 колонок с суммарным бюджетом 32 МиБ, не более 16 МиБ на колонку. Временные буферы запроса учитываются отдельно. Эти границы ограничивают кэш, а не число результатов SQL: если колонка не помещается, выполняется обычный просмотр. Небольшие выборки также идут прежним путём. Параметры томов и полей берутся из базы; год, имя тома и поле «Масса» в алгоритм не зашиты. Новые индексы в DB4 не создаются.
