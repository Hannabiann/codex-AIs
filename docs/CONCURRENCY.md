# Исполнители, отмена и Word

Tokio обслуживает сеть, а KS выполняется в отдельных системных потоках. По умолчанию их четыре:

| Исполнитель | Работа |
|---|---|
| 1 | Владелец виртуальных каталогов, фоновых очередей At/mp_g_JobsQueue, Word `/99`, неизвестных и сохраняющих состояние KS |
| 2 | Проверенные формы интерфейса АИС: главная, `d`, `hdoc`, `doc`, W, форма атрибутов и классификатор |
| 3–4 | Удаление/предварительный список, связанный поиск, 1АС, Z22.1, экспорт реестров в XLS |

Путь АИС берётся из подключения `spb.dbs` в `config.db4`. Это разделение не привязано к количеству томов или имени каталога `old`. Для неизвестных форм сохраняется последовательное исполнение у владельца. Долгое фоновое задание может задержать Word или неизвестную форму у этого владельца; отдельный исполнитель интерфейса продолжает работать.

Каждый поток содержит собственный Runtime и Db4Engine. KS-объекты с Rc/RefCell не передаются между потоками. Реплики загружают функции startup, но не исполняют вторую копию At; сигналы их локальных очередей изолированы. Именованные файловые Mutex общие, чтобы не потерять строки совместно используемых журналов.

## Настройки

В `/admin?advanced` доступны `workers` (1–32, по умолчанию 4) и `keep_alive_seconds` (0–600, по умолчанию 60). Настройки сохраняются в `codex-AIs.settings`, действуют после перезапуска и не меняют `config.db4`.

При одном исполнителе работа последовательная. При двух — владелец/интерфейс и один тяжёлый исполнитель. При трёх — владелец, интерфейс и один тяжёлый. При четырёх и более тяжёлые запросы распределяются по наименее занятому исполнителю. У каждого собственные кэши: больше исполнителей означает больше памяти. Нет обещания ускорения пропорционально числу потоков.

`queue` ограничивает общую очередь. Кроме неё предусмотрено по одному резервному месту для владельца и выделенного интерфейса; тяжёлые запросы их занять не могут. При настройках по умолчанию монитор показывает максимум 18 ожидающих запросов. Общий предел HTTP-соединений остаётся 64.

## Что означает отмена

При FIN/RST или ошибке соединения сервер ставит токен отмены конкретного HTTP-запроса. Интерпретатор проверяет его регулярно; DB-читатель — между чтениями/записями скалярных полей, ожидание Mutex/Signal — небольшими интервалами. KS `catch/finally` не может поглотить отмену. Хост освобождает удержанные именованные Mutex и состояние запроса.

В `/admin?status` сначала появляется «Отмена запрошена». После выхода исполнителя — «Отменено» и число успешно опубликованных записей DB4. Это подтверждение остановки вычисления, а не сообщение о простом исчезновении клиента. Лимита количества инструкций или общего срока отчёта не введено.

**Уже начатая публикация одной записи DB4 завершается целиком**, включая проверку и резервный образ. Между публикациями отмена вновь действует. Поэтому остановка может занять время текущей записи. Успешно сохранённая часть каскада не откатывается: общей транзакции всего каскада пока нет. При одновременном изменении одной старой редакции второй запрос получает конфликт версии. Пересекающиеся каскады могут частично выполниться до такого конфликта.

Остановка просмотра дополнительной информации ничего не удаляет. Но сам список может охватывать большую связанную группу через общие реестры, поэтому завершение огромного обхода по-прежнему может быть долгим. Пул и отмена устраняют блокировку интерфейса, не изменяя состав обхода штатного KS.

## Запись и чтение

Расчёты, обходы и создание XLS идут параллельно. Запись DB4 согласована последовательно: проверка ожидаемой записи → новый образ → журнал и резерв → публикация. В 0.16 небольшие изменения записываются страницами; большие — через замену полного файла. Подготовка не удерживает блокировку публикации. При записи страниц новые файловые чтения ждут её завершения, а уже закреплённые образы доступны из памяти. Кэши сбрасываются по поколению публикации. Один обход обратных ссылок закрепляет один образ тома и не смешивает его части. [Журнал, память и восстановление](DB40_WRITES.md).

Это не общий снимок всей базы на время многоминутного отчёта. Если одновременно меняются данные его периода, показатели могут отразить разные моменты времени. Для строгого сравнения книг используйте неподвижную согласованную копию.

## Постоянные соединения Word

HTTP/1.1 сохраняет соединение между запросами, HTTP/1.0 — при `Connection: keep-alive`. Клиент может закрыть его через `Connection: close`. Сервер поддерживает последовательные и pipelined-запросы, сохраняет границы тел и проверяет авторизацию каждого отдельно. Простой keep-alive не занимает KS-исполнитель.

`keep_alive_seconds` ограничивает только ожидание следующего запроса. Для заголовков, тела и отправки ответа остаются отдельные таймауты; часы расчёта XLS в этот интервал не входят. Параметр действует и для `/99`. Настройка keep-alive старого kodweb не заменяет эту настройку Rust.
