# Почему два удаления kodweb удваивают число чтений

19 ноября 2026 года. Продолжение [профилирования](PROFILING_0.18.md) и [анализа функций kodweb](KODWEB_CAUSES_0.18.md). Проверен `kodweb.exe` 5.3.2.120 x86 и codex-AIs 0.18 на независимой копии полного комплекта. [Численные результаты](read-amplification-0.18.json).

**Основная причина — два обхода мешают друг другу использовать общий буфер чтения тома размером 4 КиБ.** Потоки поочерёдно меняют позицию в файле, сбрасывают содержимое буфера и заново читают перекрывающиеся участки. Для `old/post1-4.db4` объём чтения увеличился с 4,32 до 18,18 ГБ, хотя фактически затронута почти та же область файла размером 1,45 ГБ.

Контроль с привязкой процесса kodweb к одному логическому процессору устранил почти весь прирост чтений. Два запроса оставались одновременными, код и параметры удаления не менялись.

## Полные операции

Удаляются два реальных документа с непересекающимися каскадами: всего шесть объектов. Выбрано штатное удаление всех связанных объектов с отметкой удаления в томе. Перед каждым вариантом использован один и тот же исходный снимок данных. У Rust четыре исполнителя KS/DB, из них два для тяжёлых запросов.

| Сервер и режим | Время выполнения, с | Процессорное время, с | Логические операции чтения процесса |
|---|---:|---:|---:|
| kodweb, два удаления по очереди | 377,993 | 342,750 | 3 596 818 |
| kodweb, два одновременно | 666,448 | 872,641 | 7 386 391 |
| kodweb, два одновременно, один логический CPU | 324,491 | 322,016 | 3 599 198 |
| Rust, два по очереди | 34,711 | 19,250 | 608 325 |
| Rust, два одновременно | 15,952 | 17,359 | 628 250 |

Это новые запуски с непрерывной записью файлового I/O через ETW, без записи стеков и переключений потоков. Они не подменяют прежние контрольные времена без профилировщика. В каждой строке один запуск, не медиана. Порядок: kodweb по очереди → kodweb одновременно → Rust по очереди → Rust одновременно → kodweb одновременно на одном CPU. Файловый кэш ОС не очищался. Машина: Windows x64, Xeon Silver 4516Y+, 6 ядер / 12 логических процессоров, около 32 ГиБ RAM.

Время выполнения — ожидание обоих ответов. Процессорное время суммирует работу всех потоков и потому может превышать время выполнения. Счётчики чтения получены через `GetProcessIoCounters`; это не количество физических обращений к накопителю.

## Где появились дополнительные чтения

Полная трасса связывает каждое файловое чтение с томом, потоком, файловым объектом Windows, смещением и размером. Потерянных событий во всех пяти трассах — ноль.

| Чтение `old/post1-4.db4` | По очереди | Одновременно | Одновременно, один CPU |
|---|---:|---:|---:|
| События чтения файла | 1 055 335 | 4 439 056 | 1 057 447 |
| Запрошено байтов | 4 322 643 988 | 18 182 365 204 | 4 331 294 740 |
| Смены читающего потока между соседними чтениями этого файла | 1 | 4 057 254 | 4 253 |

В каждой строке опыта оба рабочих потока обращались к одному файловому объекту Windows. Почти все чтения этого тома имели размер 4096 байт.

При обычном парном запуске на этот файл приходится **92,04% прироста файловых чтений ETW**. Объединение всех прочитанных интервалов составляет 1 449 112 448 байт по очереди и 1 449 619 712 байт одновременно. Общая часть — 1 449 108 352 байта: **99,96% области парного запуска уже читалось в последовательном**. Увеличивается главным образом повторное чтение тех же данных, а не область поиска.

Здесь важно считать пересечение байтовых интервалов. Чтения `[1000, 5096)` и `[1200, 5296)` имеют разные смещения, но почти полностью перекрываются. Поэтому прежний подсчёт уникальных пар «смещение + размер» в коротком окне не обнаруживал этот эффект: буфер может заполняться от новой, немного сдвинутой позиции.

Счётчики процесса и события файловой трассы приведены отдельно. Например, последовательный kodweb дал 3 596 818 операций в счётчике процесса и 3 713 608 событий `FileIO/Read` в ETW. Их область учёта различается; причина этой разницы отдельно не изолирована. Доля 92,04% вычислена только по событиям ETW, без смешивания источников.

## Механизм в коде и памяти

Штатная KS-функция `deleteDoc` для каждого удаляемого объекта перебирает поля ссылочного типа и выполняет SQL-поиск объектов, ссылающихся на него. Затем она обходит найденные объекты рекурсивно. Поэтому удаление небольшого числа документов затрагивает большие тома.

Ранее сохранённый снимок памяти объекта `post1-4.db4` содержит следующие поля. Это тот же объект тома, с которым были связаны ожидания критической секции в [предыдущем опыте](KODWEB_CAUSES_0.18.md).

| Поле относительно начала объекта | Назначение по коду | Наблюдение |
|---|---|---|
| `+0x1C` | Указатель на буфер | Один буфер в объекте тома |
| `+0x20` | Размер буфера | `0x1000`, то есть 4096 байт |
| `+0x24` | Число доступных байтов | 4096 |
| `+0x28` | Текущая позиция внутри буфера | Изменяемое состояние |
| `+0x30`, `+0x34` | Начальная позиция буфера в файле | 64-битное смещение |
| `+0x38` | Признак активного буфера | Проверяется чтением и сменой позиции |

Для исследованной сборки установлены функции:

- `0x00673FD0`: если новая позиция внутри текущего буфера, меняет внутренний курсор. Если снаружи — сбрасывает состояние буфера и выполняет переход в файле через `0x00673C00`.
- `0x00674080`: копирует доступные байты из буфера; при его исчерпании наполняет тот же буфер заново. Размер берётся из поля `+0x20`.
- `0x00673CD0 → 0x00872627 → 0x00872066 → ReadFile`: путь к чтению файла.
- `0x005F2F00`: вычисляет позицию блока, меняет позицию и вызывает `0x00674080` с тем же объектом тома.

Адреса относятся только к проверенному EXE. Назначения функций восстановлены по инструкциям и наблюдаемому состоянию, а не по отсутствующим отладочным именам.

Упрощённый пример последовательности:

1. Поток A загружает участок файла в общий буфер и использует его для нескольких небольших чтений.
2. Поток B переходит к своей позиции вне этого участка. Прежний буфер сбрасывается.
3. Поток A продолжает свой обход, но нужного участка в буфере уже нет. Выполняется новое чтение 4096 байт, часто перекрывающее предыдущее.

Блокировка защищает общее состояние от одновременного изменения, но не сохраняет отдельную позицию и буфер для каждого обхода.

## Что проверил контроль с одним CPU

Привязка изменила только допустимые процессоры процесса kodweb: с 12 логических процессоров на один. Оба HTTP-запроса были запущены одновременно и обслуживались разными рабочими потоками.

Количество чередований читающих потоков на проблемном томе снизилось с 4 057 254 до 4 253. Число чтений этого тома вернулось почти к последовательному: 1 057 447 вместо 1 055 335. Общий счётчик процесса также вернулся к исходному уровню: 3 599 198 вместо 3 596 818.

Это причинный контроль влияния чередования обходов: параметры запроса и данные одинаковы, а изменение расписания потоков почти убирает лишний ввод. В сочетании с устройством общего буфера он объясняет основной прирост чтений в данном случае. Привязка к одному CPU использована как диагностический приём; работа отчётов и смешанной нагрузки с такой настройкой не измерялась.

## Почему Rust ведёт себя иначе

В codex-AIs [результаты отбора и обратные ссылки](../src/db/shared_query.rs) разделяются между исполнителями. Один исполнитель строит недостающий результат, другой ожидает его и использует готовые данные. Контексты чтения файлов и их позиции остаются локальными; [чтение скалярных полей](../src/db/mainkey.rs) использует страницы по 64 КиБ и локальный кэш из восьми страниц.

Здесь описана измеренная версия 0.18. В 0.23 ёмкость увеличена до 64 страниц по результатам [отдельного сравнения кэшей](SCALAR_CACHE_0.23.md).

Для того же `post1-4.db4` Rust выполнил 50 084 файловых чтения по очереди и 50 173 одновременно. Общий счётчик операций чтения вырос лишь с 608 325 до 628 250. При этом Rust запросил около 31,2–31,3 ГБ данных: преимущество не означает меньший объём байтов во всех сценариях. Существенны размер обращений, повторное использование результатов и отсутствие конкурирующих обходов одного общего буфера.

## Проверка результата и границы вывода

Во всех вариантах проверены одинаковый состав каскада, отсутствие шести объектов и создание шести архивов `.kod`. Полностью сопоставлены декодированные данные архивов и записи изменённых `work.db4`/`workpost.db4`; результаты приведены в JSON. Время и порядок записей аудита не включены в побайтовое сравнение.

Установлена причина основного прироста чтений именно этой пары удалений. Она не объясняет все затраты одиночного удаления, другие наборы документов или формирование отчётов Excel. Процессорное время включает также SQL, интерпретацию KS, синхронизацию и работу с объектами; их полный вклад этим опытом не разделён.
