# Журналы и ежедневные архивы

С 0.29 каталог по умолчанию — `Log-codex-AIS` внутри корня базы. Например, для `C:\kodeks` это `C:\kodeks\Log-codex-AIS`. Каталог создаётся при запуске. Явный `KODEKS_LOG_DIR` сохраняет приоритет; фактическое переопределение показано в `/admin/`.

| Файл или каталог | Содержимое |
|---|---|
| `error.log` | Ошибки HTTP/KS, фоновых заданий, инициализации и необработанные Rust panic |
| `access.log` | Завершённые HTTP-запросы и фоновые операции: адрес клиента, пользователь, исполнитель, маршрут, длительность, результат |
| Остальные `.log` | Журналы штатных KS, перенаправленные из логического `Log`/`log` |
| `OLD_Log/*.zip` | Завершённые дневные сегменты журналов |

`error.log` и `access.log` записываются в UTF-8. Дата содержит миллисекунды и часовой пояс сервера. Ошибка запроса содержит ID операции, адрес клиента, пользователя, номер исполнителя KS/DB, URL, длительность и сообщение интерпретатора. С 0.29.1 ошибка KS дополняется многострочным снимком выполнения; обычные HTTP/сетевые ошибки и записи доступа остаются однострочными. Обычный ответ 401 при запросе авторизации остаётся в `access.log`, без отдельной ошибки. Незавершённые операции видны в `/admin?status`.

Заголовки Authorization/Cookie и сырое тело формы в серверные журналы не копируются. В `access.log` и кратких HTTP-ошибках URL сохраняет только имена параметров и числовые координаты документа. В подробной ошибке KS URL содержит параметры для воспроизведения, кроме распознаваемых паролей, токенов и идентификаторов сеанса. Снимок переменных может содержать данные, которые обрабатывал скрипт; журналы не предназначены для публикации вместе с кодом.

## Подробная ошибка KS — 0.29.1

В 0.31 устранена подготовка снимков для простых `catch`, которые заведомо
поглощают исключение: пустого обработчика, пропуска итерации или возврата
скалярного значения. Такие штатные ветки не записывались в `error.log`,
но раньше тратили время на форматирование. Полная диагностика настоящих
ошибок и исходный контекст повторного `throw` сохранены.
[Профиль и проверка на отчёте](COURT_TOTALS_0.31.md).

Снимок записывается до очистки контекста запроса, в том числе для ошибок `Document.Execute`, фоновых заданий и запуска каталога:

1. Дата, время, URL и сообщение об ошибке.
2. Имя исходного KS, номер строки и смещение. Текст показан до ошибочного оператора; строка отмечена `>>>`, сам оператор — `<< throw >>`, `<< MissingHost >>` и т. п. В журнал попадает исполняемый текст после необходимых преобразований совместимости.
3. Активные вызовы от входа к месту ошибки, места вызова, имена параметров и переданные значения. Для скалярных аргументов сохраняются значения при вызове, для объектов показано их состояние в момент ошибки.
4. Локальные переменные и константы каждого вызова, глобальные значения и дополнительные области видимости. Указаны имя, тип и значение. Документы представлены OID и контекстом базы; диагностика не читает дополнительные записи DB4 и не вызывает свойства объектов.

Пример на искусственном скрипте:

```text
Source: example.ks:3 (UTF-8 byte 57)
Script through the failing statement (>>>):
         1 | function fail(n) {
         2 |     var attrId = n;
>>>      3 |     << throw >> 'Unknown attribute';

Stack call function (entry → failure):
#1 Function: fail / fail(n)
Arguments (scalar values at call; objects show their current state):
Name    Type    Value
0: n    number  17
Local variables and constants
attrId  number  17
```

Это стек незавершённых вызовов, как `Stack call function` у kodweb, а не история всех ранее выполненных функций. Перехваченное `try/catch` исключение само по себе в журнал не записывается. `throw;` сохраняет первоначальное место ошибки; новая ошибка в `finally` показывает новое место. Следующий запрос получает собственный снимок.

Если том содержит только байткод, журнал показывает адрес и код ошибочной инструкции, соседние декодированные инструкции, стек и значения. Исходный KS в этом случае не выдумывается. Оператор выделяется с точностью до выполняемого оператора KS; это не пошаговая трассировка каждого подвыражения.

Значения с распознаваемыми именами паролей, Cookie, Authorization и токенов скрываются. Потоки, содержимое вложений и ленивые наборы записей не разворачиваются. Циклы объектов отмечаются явно. Для устойчивости при ошибке большие значения сокращаются: строка — 4096 символов, объект — до 128 членов и двух уровней, диагностический текст — около 8 МиБ. Длинный исходник сокращается после первых 256 КиБ с сохранением участка перед ошибкой. Все сокращения обозначены в журнале.

Весь блок между `BEGIN KS DIAGNOSTIC` и `END KS DIAGNOSTIC` добавляется одной согласованной записью. Параллельные ошибки не перемешиваются; ежедневная ротация переносит блок целиком. Подробный текст не отправляется в HTTP-ответ и не дублируется целиком в консоль.

KS-журналы сохраняют штатную кодировку и содержимое. Для имён `Log/access.log` и `Log/error.log` используются `ks-access.log` и `ks-error.log`, чтобы KS не мог обнулить серверный журнал. Логические файлы в корне базы, например `time.log`, по-прежнему получают префикс `root-`. Старые журналы прежних версий остаются на прежнем месте; новый выпуск не объединяет их автоматически с текущим днём.

## Настройка срока хранения

Откройте **Администрирование → Установки → Расширенные настройки** (`/admin?advanced`). Параметр **«Хранить ZIP-архивы логов, дней»** сохраняется в `codex-AIs.settings`:

```ini
log_retention_days=7
```

Допустимы значения от 0 до 3650. По умолчанию сохраняются архивы за семь предыдущих календарных дней плюс текущие журналы. Например, 26 ноября остаются архивы за 19–25 ноября; более ранние удаляются. Значение **0** отключает удаление архивов по сроку. Изменение применяется после перезапуска, как остальные параметры этой формы.

В `/admin?pref` убраны поля путей и выбора формата протокола kodweb. Вместо них показаны каталог Codex-AIs, назначение журналов и ссылка на расширенные настройки. То же пояснение добавлено на стартовую страницу `/admin/` и в справку установок. Остальные поля штатной формы сохранены.

## Как происходит ротация

1. При смене локальной даты текущие `.log`, включая вложенные KS-журналы, перемещаются в отдельный сегмент внутри `OLD_Log`. Переключение согласовано с записью; следующий вызов уже открытого KS-файла переоткрывает текущий журнал.
2. Отдельный поток сжимает сегмент в ZIP64 с Deflate. Сжатие не занимает исполнителя KS/DB и не удерживает блокировку записи журналов. Файлы читаются порциями по 64 КиБ.
3. Завершённый ZIP синхронизируется с диском и публикуется переименованием временного файла. Исходный сегмент удаляется после публикации. После прерывания сжатия незавершённый сегмент обрабатывается повторно при запуске.
4. По сроку удаляются только архивы с именами, которые формирует этот механизм. Текущие журналы, незавершённые сегменты и произвольно названные пользовательские файлы не удаляются.

Имя архива начинается с даты сегмента, затем содержит уникальный суффикс: `2026-11-25-1234-….zip`. Обычно за день получается один архив; при восстановлении после прерванного переключения возможно несколько сегментов одной даты. Проверка даты происходит перед записью и фоновым потоком раз в 30 секунд. Если сервер был выключен ночью, предыдущий день архивируется при следующем запуске.

Ошибки серверной записи журналов также выводятся в stderr. Если каталог недоступен уже при запуске, причина остаётся в консоли. Серверная запись не удерживает блокировки монитора или DB4. Изменение формата и ротация не меняют протокол записи базы.

## Проверки 0.29

Проверено на Windows x64, на полном контрольном комплекте из 49 томов:

- главная, `/admin?pref`, сведения о программе, справка и расширенные настройки;
- ошибки 404 и KS 500, 24 запроса с восемью параллельными клиентами, сокрытие секретного параметра URL;
- штатные KS-журналы в новом каталоге и явный `KODEKS_LOG_DIR`;
- ошибка запуска при отсутствующем `config.db4` в отдельном тестовом каталоге;
- смена дня при запуске: шесть журналов, в том числе файл 16 МиБ; все байты архивов совпали с исходными файлами;
- сохранение сроков 0 и 2 через штатную форму, применение 2 после перезапуска, граница хранения 7 дней;
- 19 автоматических тестов Rust, включая 800 записей из восьми потоков, четыре потока записи одновременно со сжатием, открытый KS-файл после ротации и повторное сжатие прерванного сегмента;
- независимая распаковка ZIP и проверка CRC через Python `zipfile`, включая кириллические имена.

Новый механизм не добавляет зависимостей от Windows-служб или внешнего архиватора. Проверка исполнения 0.29 на Linux и FreeBSD ещё требуется.

## Проверки подробной диагностики 0.29.1

На Windows x64 прошёл 31 автоматический тест; четыре теста с отдельными закрытыми DB4-фикстурами остаются отключёнными по умолчанию. Проверены вложенные вызовы, замыкания, параметры и локальные значения, `throw mp_xCreate(...)`, повторный выброс исключения, новая ошибка в `finally`, HTML-подстановки и ошибки байткода. Шесть потоков записали 48 полных диагностических блоков без перемешивания.

На искусственных KS результат выполнения обычных функций, `eval` и перехваченных исключений совпал с 0.29. Это проверка интерпретатора и записи журнала; новая подробная диагностика ещё не проверена через HTTP на полном комплекте базы и на FreeBSD/Linux.
