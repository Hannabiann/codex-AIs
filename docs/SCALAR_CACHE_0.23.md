# Кэш страниц: выбор для 0.23

23 ноября 2026 года. [Численные результаты](scalar-cache-0.23.json).

**В 0.23 выбрано 64 страницы по 64 КиБ.** На трёх одновременных удалениях медиана времени снизилась с 20,77 до 16,30 с относительно восьми страниц: на 22%. Логический объём чтения процесса уменьшился с 30,18 до 15,51 ГиБ. Переход с 32 на 64 страницы дал ещё 8% по времени удаления и 18% по объёму чтения. Ускорение формирования отчётов не подтверждено.

## Что именно изменено

Это локальный кэш [чтения атрибутов и ссылок объектов](../src/db/mainkey.rs), а не весь кэш базы. При заполнении вытесняется страница, к которой дольше всего не обращались. У каждого контекста чтения тома свои страницы; они выделяются по мере чтения. При 64 страницах помещается до 4 МиБ данных на контекст чтения, при 32 — 2 МиБ, при 8 — 512 КиБ. Суммарный расход зависит от числа открытых контекстов чтения и исполнителей.

Размер страницы остаётся 64 КиБ. Он не задаёт внутренний формат DB40 и не является размером страницы журнала восстановления. Кэши индексов и результатов запросов работают отдельно. Правила закрепления старых образов и сброса контекстов чтения после записи сохранены.

## Условия измерения

Полный контрольный комплект, Windows x64 в виртуальной машине, Xeon Silver 4516Y+, доступные 6 ядер / 12 логических процессоров, 32 ГиБ памяти. Пул одинаковый: шесть исполнителей KS/DB, из них четыре для тяжёлых запросов; очередь 16, HTTP-соединений 64.

Во всех вариантах использовалась одна измерительная сборка, менялось только число страниц. Для каждого размера выполнены три независимых запуска с одинаковым исходным состоянием данных. Порядок: 8 → 32 → 64; затем 32 → 64 → 8; затем 64 → 8 → 32. Процесс перед сценарием новый. Файловый кэш ОС не очищался. «Первый расчёт» означает первый расчёт в процессе, а не чтение с физически холодного накопителя.

В таблицах — медианы трёх запусков, кроме отдельно обозначенных контролей. Время выполнения измерено до последнего ответа. Процессорное время суммирует работу всех потоков и может превышать время выполнения. Память — медиана наблюдавшихся пиков частной памяти процесса, шаг наблюдения 200 мс. Чтения получены из счётчиков процесса: это логический объём, не физический трафик накопителя.

При 64 страницах пик памяти в этой серии выше на 254 МиБ, чем при восьми. Число промахов уменьшается с 36 660 до 26 260, но это малая часть примерно 10,2 млн логических операций чтения процесса. Снижения полного времени расчёта не видно. Диапазоны первого расчёта существенно перекрываются: 76,80–88,63 / 76,68–86,97 / 69,71–88,01 с. Эти данные не дают оснований обещать ускорение Excel-отчётов от увеличения данного кэша.

Для каждого размера дважды проверен повторный расчёт тех же четырёх отчётов в том же процессе. Во всех шести контролях у кэша скалярных страниц **ноль попаданий и ноль промахов**: нужный результат уже обслуживают другие уровни кэширования. Время этих контролей также колебалось; отдельные быстрые запуски не использовались как доказательство преимущества размера страниц.

## Проверка результата и записи

Все 63 XLS измерительной серии побайтно совпали с контрольной книгой. Во всех 12 сериях удаления проверены ожидаемые 14 объектов, отсутствие их карточек, сохранность родительских дел и содержимое KOD. Архивы одних и тех же объектов совпали между вариантами. Главная, просмотр документа и проверка соединения Word отвечали под нагрузкой; максимальный измеренный ответ — 383 мс.

При подготовке обнаружена отдельная ошибка Windows: полная замена тома журнала действий могла завершиться `DB40 backup publication: отказано в доступе`. Причина воспроизведена на отдельных файлах: переименование поверх резервного файла не удавалось, пока его держал старый контекст чтения. Исправлено обновление резерва с предварительным сохранением старого образа для такого контекста чтения. Том публикуется после синхронизации резерва; [протокол восстановления](DB40_WRITES.md) сохранён. Все приведённые сравнения выполнены с одинаковым исправлением.

Обычная сборка без измерительных счётчиков также прошла смешанный сценарий: три удаления, 14 объектов и отчёт с тем же XLS. Штатный kodweb подтвердил отсутствие всех 14 объектов и доступность обоих родительских дел. Пройдены 429 обычных тестов и четыре дополнительные проверки на нативных томах: восстановление после имитации сбоев, сохранность старого контекста чтения, восстановление перед использованием общего кэша и совпадение скалярного чтения с полными записями. Два новых регрессионных теста проверяют повторную полную публикацию с открытым старым контекстом чтения и резерв, связанный с текущим томом жёсткой ссылкой.

Выбор 64 страниц отдаёт приоритет удалению и сокращению чтений, при измеренном увеличении памяти отчётов. Это результат проверки данного комплекта и этой машины. Большие страницы 128/256 КиБ и другие размеры пула здесь не сравнивались; измерительные счётчики в обычную сборку не включены.
