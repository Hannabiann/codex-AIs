# Первичная регистрация и входящие документы — 0.21

В версии 0.21 работают штатные формы регистрации из томов АИС. Меню, поля и правила заполнения формируются KS-скриптами установленного комплекта.

| Пункт меню | Адрес | Проверенный сценарий |
|---|---|---|
| Первичная регистрация | `/30` → `/20a?regdelo&instanc=1&` | Новое дело первой инстанции, истец и ответчик, исковое заявление, статистическая карта, результат регистрации |
| Регистрация входящих документов к судебному делу | `/32` → `/20a?regdoc&instanc=1&` | Выбор существующего дела, входящее письмо, заявитель из участников дела, входящий номер и результат регистрации |

Обе ссылки доступны в штатном меню главной страницы. Новые записи сохраняются в подключённые рабочие тома DB4. Следующий номер дела и следующий входящий номер хранятся в существующих полях `config.db4`.

## Что исправлено

- Реализован хостовый объект `KJSON`: карточки участников передаются как JSON, без исполнения входного текста как KS. Чтение отсутствующего необязательного свойства больше не создаёт лишние поля карточки.
- Исправлена работа методов и полей классов KS, импортируемых через `Execute`. Это требуется редактору участников и расчёту сроков.
- Поддержаны используемые скриптами переносы строки после `return`, необязательные даты и обратное преобразование даты из GMT. Пустая необязательная дата попадает в штатный `try/catch`.
- Числовые поля DB4 сохраняют отрицательное служебное значение `-1` в исходном 32-битном представлении. Проверка положительных идентификаторов объектов остаётся отдельной.
- HTTP-парсер принимает повторяющиеся служебные поля штатных регистрационных форм. Для управляющих параметров, включая `mode`, проверка неоднозначности сохранена.
- Динамические JavaScript и CSS получают соответствующий `Content-Type`; браузер не блокирует их из-за `nosniff`.
- Регистрационные скрипты авторизованного пользователя могут сохранять документы и два регистрационных счётчика. Счётчики обновляются существующим механизмом записи DB4 с проверкой прежнего значения.
- `synchronized` в KS использует общую блокировку для исполнителей одного каталога данных. Выделение входящего номера больше не является независимым чтением и записью в каждом исполнителе.
- Загрузка вложений принимает двоичный `multipart/form-data`: содержимое файла не преобразуется в текст. Поддержаны временные файлы, перенос в штатное хранилище при регистрации и удаление вложения из незавершённой формы.
- Исправлены пустые группы регулярных выражений и `FilePath` без имени, которые использует штатный код работы с путями. Файловые потоки поддерживают последовательное чтение строк и байтов; вкладка «Файлы к документу» открывается после сохранения.

## Хранение вложений

В проверенном комплекте формы сохраняют вложения отдельными файлами в каталог `graf_files`, заданный параметром `FileDocPath`: подпапка дела, затем внутренний номер документа. Это поведение штатных KS. Карточки и связи записываются в DB4, сами эти вложения — в файловое хранилище. Для переноса базы нужны оба хранилища.

Rust читает пути из настроек базы. Если отдельный временный каталог не задан, загрузки размещаются в `.codex-upload-temp` рядом с томами. Команды копирования, перемещения и удаления пустого каталога из `Shell.Execute` исполняются файловыми функциями Rust в пределах настроенных каталогов. Внешняя командная оболочка для этого не запускается.

Размер одного HTTP-запроса загрузки ограничен 64 МиБ, включая поля формы. Файл копируется через промежуточный файл с синхронизацией на диск и переименованием. Общей транзакции для карточки DB4 и внешнего вложения пока нет; прерывание всего процесса регистрации на каждом этапе отдельно не проверялось.

## Проверка с kodweb

Сравнение выполнено 22 ноября 2026 года на полном контрольном комплекте: 49 подключённых томов. Эталон — `kodweb.exe 5.3.2.120`, 32 бита. В обоих вариантах использовались одинаковые исходные данные и тестовые участники.

Последовательность в браузере: открыть первичную регистрацию, добавить истца и ответчика, прикрепить TXT и зарегистрировать дело с исковым заявлением; открыть регистрацию входящих к этому делу, прикрепить RTF и зарегистрировать письмо от истца. Затем открыть оба документа заново, перейти на вкладку «Файлы к документу» и скачать вложения.

| Проверка | Результат |
|---|---|
| Поля дела, первичного документа, статистической карты и письма | Совпали после исключения времени операций и автоматически сгенерированного поля «Уникальный код» |
| Стороны дела, участники и адреса | Совпали; отличаются только отметки времени создания и изменения |
| История первичного документа | Совпала после нормализации времени событий |
| Регистрационные счётчики | Совпали в `config.db4` |
| Полная сверка прочитанных записей изменённых томов | 478 записей рабочего тома, 6 записей тома участников и 3399 записей конфигурации; других различий не найдено |
| Чтение оригиналом после записи Rust | Kodweb открыл карточки и выдал вложения, созданные Rust |
| TXT и RTF после регистрации | Скачаны через браузер в kodweb и Rust; SHA-256 совпал с исходными файлами. Файлы, записанные Rust, также скачаны без изменения через kodweb |
| Двоичная загрузка с кириллическим именем в Rust | Файл 2 МиБ принят без изменения байтов; после кнопки «Удалить» исчез из формы и временного каталога |
| Отмена первичной регистрации | В обоих серверах черновик удалён; при отсутствии более поздней регистрации номер дела снова доступен |
| Восемь открытий первичной регистрации, четыре параллельных запроса | Восемь различных последовательных номеров дел и входящих документов; kodweb затем прочитал следующий номер |
| Обе формы с `multipart/form-data` | Сохранение и страницы результата прошли; отдельно проверена обычная URL-кодированная отправка |

Обе регистрации завершены кнопками штатных форм в браузере. Проверены результат сохранения, повторное открытие карточек после перезапуска сервера и скачивание файлов. Предпросмотр UTF-8 TXT без BOM использует Windows-1251 и показывает искажённую кириллицу в обоих серверах; байты скачанного файла сохраняются.

Сборка `cargo build --release --locked` прошла. Во внутреннем наборе проверок — 379 успешных тестов, 63 проверки с внешними данными по умолчанию пропущены. Полный сценарий выше и сверка снимков DB4 проверены отдельно. В набор входят проверки журнала восстановления, JSON, дат, классов KS, повторяющихся полей, двоичного multipart и границ файлового доступа.

## Границы проверки

Проверка выполнена на Windows: первая инстанция, исковое заявление и входящее письмо, TXT и RTF во внешнем хранилище. Другие виды документов, регистрация в апелляции и кассации, помесячные и сетевые хранилища, импорт из внешних систем и электронная подпись этой проверкой не охвачены. Сквозная проверка вложений на Linux и FreeBSD ещё нужна.

Открытие первичной регистрации уже резервирует черновик и номера — так устроен штатный скрипт. Запись каждого тома защищена журналом восстановления. Единой транзакции, откатывающей весь регистрационный сценарий сразу в нескольких томах, пока нет.
