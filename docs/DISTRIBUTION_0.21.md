# Автоматическое распределение и восстановление КП — 0.21

Версия 0.21 подготовлена локально. Сравнение выполнено 22 ноября 2026 года на полном контрольном комплекте: 49 подключённых томов, включая архивы. Эталон — kodweb.exe 5.3.2.120, 32 бита.

## Журнал распределения на Unix — 0.25.2

Функция `PrintToAutoBlockedJudgesLog`, вызываемая из скомпилированного KS распределения, обращается к каталогу `Log`. До 0.25.2 проверка пути принимала это написание на Windows, но на Unix сравнивала его с `log` с учётом регистра. Поэтому `MkDir('Log')` завершался ошибкой до записи журнала.

Теперь только логическое имя каталога журналов распознаётся без учёта регистра на всех платформах. `Log`, `log` и `LOG` направляются в `KODEKS_LOG_DIR` либо автоматически выбранный каталог журналов. Настоящий путь к базе на Unix и имена файлов сохраняют регистр; ограничения записи и проверки переходов за пределы каталога остаются прежними.

Проверены создание подкаталога через `MkDir`, запись, закрытие и повторное открытие файла, абсолютный путь и отклонение попыток записи в тома или за пределы каталога. Файловые проверки прошли на Windows. Сам сервер на FreeBSD в этой серии не запускался; исправление следует из различия ветвей сравнения пути для Windows и Unix.

## Какие формы исполняются

Автоматическое распределение открывается по адресу `/20a?Raspred_Del_Auto&inst=1`. В проверенной базе это объект `730099157` в `spb.dbs`: исходного текста нет, логика и HTML находятся в 344 009 байтах скомпилированного KS. Rust исполняет этот объект. Правила выбора судьи, категории, коэффициенты и ограничения берутся из базы.

Массовый пересчёт доступен через «Настройка распределения» → «Восстановить КП судей», адрес `/20a?restorekp`. Здесь исполняется исходный KS объекта `730099161`.

**КП** — имя поля судьи, используемого при распределении для учёта расчётной нагрузки. Восстановление КП заново вычисляет показатель за выбранный период. Для первой инстанции штатный скрипт отбирает статкарты по дате иска и первому судье в составе суда, учитывает установленные типы записей о банкротстве, суммирует коэффициенты сложности категорий и умножает сумму на поле судьи «Рабочий КС». Последнее служит множителем нагрузки. Эти обозначения сохранены по интерфейсу АИС; отдельная словесная расшифровка букв в исследованном скрипте не установлена.

Режим «только вычислить» показывает старое и новое значения. Режим восстановления записывает новый КП в штатный DB4. Это пересчёт показателя, а не восстановление удалённых документов.

## Исправления исполнения

- Добавлены используемые распределением операции скомпилированного KS: дробные константы, унарный минус, выбрасывание исключения и анонимная функция без аргументов.
- У объекта `File` появилась собственная настройка `CharSet`, нужная для чтения правил. Она не меняет кодировку других открытых файлов.
- SQL сортирует поле `LongDouble` по его штатному двоичному представлению. Отображение такого поля больше не превращает ненулевой коэффициент в пустую строку.
- `String.isDigit()` проверяет всю непустую строку. Раньше девятизначные номера документов не проходили проверку, поэтому форма могла завершиться без фактического назначения.
- Ошибка незаполненной необязательной даты обрабатывается штатным `try/catch`. Дописывание истории через `Stream.skip()` сохраняет прежние события.
- Умножение дробных `LongDouble` сохраняет полное промежуточное произведение до округления. Малые коэффициенты распределения больше не вызывают переполнение из-за длинной дробной части. Предел результата остаётся 28 десятичных знаков после запятой; это не полная 192-битная арифметика оригинала.
- При массовом восстановлении КП отбор судей учитывает историческую принадлежность рабочему разделу, как kodweb. Для проверенной версии скрипта адаптер применяется по контрольному хешу. Актуальные поля и отметки удаления читаются обычным способом; правила остальных SQL-запросов не изменены.
- Перед сериализацией DB4 проверяются число скалярных полей в заголовке и их расположение перед потоками. Запись с устаревшим счётчиком отклоняется до публикации.

Открытие формы распределения в оригинале обновляет рабочие коэффициенты судей. Этот шаг теперь разрешён и при открытии формы Rust авторизованным пользователем; штатные проверки доступа продолжают исполняться.

## Причина `Bad field type` в первоначальном опыте

Ошибка находилась во вспомогательном коде подготовки тестовых данных: он удалял поля непосредственно из `Record.fields`, но сохранял старое значение `Record.flags`. В этом формате поле, названное `flags` в Rust, содержит число скалярных полей. Например, после удаления трёх ссылок оставались 197 скалярных полей и один поток, а заголовок по-прежнему содержал 200.

Стек исключения kodweb показал чтение полей через `0x006fa070` и отказ фабрики типа поля `0x006f91c0` с кодом `0x267` — ресурсом «Bad field type». Ошибка возникала до алгоритма выбора судьи. Неверный счётчик заставлял штатный модуль чтения обрабатывать данные за границей ожидаемого набора полей.

Контрольный опыт изменил только счётчики заголовков девяти подготовленных записей; область, порядок и содержимое полей остались одинаковыми. После этого kodweb сформировал форму и сохранил назначения. Причина подтверждена этим опытом, а прежнее ограничение сравнения первичного распределения снято.

Обычный путь `Document.Write` уже пересчитывал заголовок через `canonicalize`; вспомогательный код обходил этот шаг. Подготовка исправлена. Дополнительно сам сериализатор теперь отклоняет неправильный счётчик и скалярные поля после потоков. Прежней проверки полного обратного декодирования было недостаточно: модуль чтения Rust мог разобрать все поля, не используя отдельный скалярный счётчик.

## Границы проверки

Сравнение 127 документов относится к перераспределению существующих дел на исходных данных. Проверена первая инстанция с правилами контрольного комплекта. Другие конфигурации распределения, инстанции и сочетания отпускных ограничений не покрыты этой серией.

Регрессионный набор: 365 тестов прошли, ошибок нет. В него входят проверка дробной арифметики, порядка `LongDouble`, операций скомпилированного KS, истории, заголовков записей и восстановления по журналу. Отдельная проверка на подготовленных записях подтвердила, что при устранении `Bad field type` изменились только счётчики заголовков.

Публикация каждого объекта использует существующую проверку ожидаемой редакции и журнал восстановления DB4. Несколько объектов одного распределения не образуют единую транзакцию: сбой между их записями требует проверки уже выполненных назначений.
