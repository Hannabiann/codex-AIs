# Общий кэш и одновременные удаления: 0.18

[Сокращения и термины: отчёты, ETW, KS/DB, Excel и другие обозначения](GLOSSARY.md).

18 ноября 2026 года. Windows Server 2025 x64, Xeon Silver 4516Y+, 6 ядер / 12 логических процессоров, 32 ГиБ RAM. Независимая копия полного комплекта из 753 753 файлов; исходный каталог не использовался для записи.

## Что измерялось

Два реальных документа отправляются на удаление отдельными одновременными HTTP-запросами. Выбраны те же A и B, что в [предыдущей проверке](REAL_DELETION_0.17.1.md): входящий отзыв и определение 2026 года (каскады 1+5 объектов), ходатайство и определение 2020 года (5+4). Корневые документы находятся в архивных томах размером 1,64 и 6,02 ГБ. Архивы читаются, а отметки удаления записываются в рабочие тома.

Штатный режим «Удалить все объекты»: `deleteobj=1`, `fhole=1`, `flong=0`, `fview=0`. Выгрузка KOD и журнал действий входят во время ответа. Дело и защищённые контрольные объекты не удаляются; каскады выбранной пары не пересекаются.

## Первый обход после запуска процесса

Время от отправки пары до завершения обоих ответов. Для Rust — медиана трёх запусков каждой версии, для обычного kodweb 5.3.2.120 — один запуск каждой пары.

| Документы | Rust 0.17.1, с | Rust 0.18, с | kodweb.exe, с | Ускорение Rust |
|---|---:|---:|---:|---:|
| 2026 | 26,739 | 17,319 | 737,179 | 1.54× |
| 2020 | 28,219 | 18,089 | 1163,657 | 1.56× |

| Группа | Сервер | Минимум–максимум, с |
|---|---|---:|
| 2026 | Rust 0.17.1 | 26,078–39,931 |
| 2026 | Rust 0.18 | 17,194–17,789 |
| 2020 | Rust 0.17.1 | 26,393–30,011 |
| 2020 | Rust 0.18 | 18,039–18,488 |

Перед каждым запуском восстановлен один свежий снимок текущей копии. Предшествующие пользовательские изменения сохранены. Старый и новый Rust чередуются по порядку; затем выполнены два запуска kodweb и отдельная проверка прогрева. Кэш ОС не очищался. «Первый обход» означает пустой кэш удаления процесса, а не холодный накопитель: до таймера открываются главная и атрибуты двух документов. Предпросмотр удаления не выполняется.

Во время таймера не выполнялись сборка, резервное копирование или диагностические HTTP-запросы. Использован тот же очищенный EXE, который приложен к выпуску. Все времена, CPU и логическое I/O Windows сохранены в [JSON](shared-cache-0.18.json); счётчики I/O не являются физическим трафиком диска.

## Прогрет только один исполнитель

Отдельный опыт на паре 2020 года, по одному запуску каждой версии: сначала один предварительный просмотр, затем два одновременных удаления. Стоимость просмотра показана отдельно и не включена во время удаления.

| Версия | Предпросмотр одного документа, с | Два удаления после него, с |
|---|---:|---:|
| 0.17.1 | 14,084 | 16,903 |
| 0.18 | 14,533 | 3,574 |

В 0.17.1 второй тяжёлый исполнитель строит собственный кэш. В 0.18 он может использовать результат первого. Это проверка повторного использования данных, а не измерение предельного числа клиентов.

## Проверка результата и восстановления

Все 16 серий проверены по ожидаемому набору удалённых объектов, KOD, отсутствию объектов и доступности дела. Созданы 123 KOD; 108 файлов Rust полностью сопоставлены с результатами обычного kodweb. Сравниваются декодированные поля, потоки и метаданные, поэтому различие сжатия допустимо.

В 28 сравнениях целых `work.db4` и `workpost.db4` совпали наборы OID, отметки и поля 14 322 полных записей суммарно. Аудит и служебные счётчики config.db4 не сравниваются побайтно: время и порядок запросов различаются.

Отдельно проверены отказ построителя, отмена ожидания, смена поколения во время построения, undo/redo при заполненном кэше, повреждённый журнал и аварийное завершение дочернего процесса. [Протокол проверок](VALIDATION_0.18.md).

## Почему меняется время

Исполнители больше не повторяют одинаковый обход обратных ссылок по архивам. Один строит индекс, остальные используют неизменяемые массивы. Публикация рабочего тома не выбрасывает результаты для неизменённых архивов. Номер поколения обновляется под блокировкой публикации, в том числе после восстановления журнала.

Публикации DB4 остаются согласованными последовательно; общий кэш ускоряет подготовку, а не разрешает одновременно перезаписывать одни страницы. Транзакция охватывает одно изменение тома, а не весь каскад. На другой базе, при плотных связях, другом состоянии кэша или пересекающихся каскадах результат может отличаться. Годовые отчёты, kodweb64, Linux и FreeBSD в этой серии повторно не измерялись.
